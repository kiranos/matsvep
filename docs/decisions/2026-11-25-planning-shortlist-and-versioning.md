# Planning shortlist and versioned decisions

The first planning prepares favourite and discovery pools after SQL hard filters. It scores every unrated discovery for the configured Content prefilter, retains wishlisted recipes, and stores the resulting recipe IDs in `plan_candidate`. Database triggers increment `household.state_version` for recipe status, rating, wishlist, carry-over and setting changes. A plan records the state and config versions used to build its shortlist; a mismatch rebuilds it before the next deck. Later picks and shuffles recheck current hard filters. A valid recipe picked from search is added to the shortlist before re-ranking. This avoids a full-catalogue scan on ordinary swipes while allowing a newly rated or wishlisted recipe to enter the pool.

Carry-overs are placed before sampled choices on their best open day and count toward the favourite quota. The second split planning subtracts favourites already chosen in the first part from the whole-week target. The configured profile order puts constrained days first. The seeded softmax, pairwise swap pass and dish-group-unique decks are deterministic for identical inputs.

Choose, replace, autofill and shuffle lock the plan row, compare the expected version, write slots and increment the version in one transaction. A stale version raises `plan_version_conflict`. Chosen slots store reason codes, parameters and the Scorer breakdown in `explanation_json`; proposed slots do not store a permanent explanation. The API controllers remain a later task.

Similar rated recipes are matched only for cards whose explanations are returned. Matching every member of the saved shortlist on each swipe delayed re-ranking without affecting scores. The database benchmark times the full manager path, including MySQL queries, candidate hydration, scoring and writes, on generated production-scale rows.
